# D1 — Documentation and interview pack (Opus)
Read: `docs/plan/PLAN.md`, `docs/plan/EXPLAINABILITY.md`, all handoffs, `docs/AUDIT_LOG.md`, `docs/EXPERIMENTS.md`,
`docs/bench.md`, model cards, `artifacts/registry.json`; read source where needed to explain it accurately.
Reader: a final-year B.Tech student who must defend every line and found the previous project too hard to
explain. Short sentences, plain words, no filler. **Only measured numbers**, each traceable to a card, bench file
or handoff. Where something was not built or did not work, say so. Team and urgency are the project's rubric: say so.
Write:
1. `README.md`: what it is, live links (placeholders for the candidate), 60-second quickstart, the ASCII diagram,
   results table, two screenshots (take them with Playwright), data source and licence, limitations.
2. `docs/ARCHITECTURE.md`: six components and two surfaces, data flow, schema, each design decision with the rejected alternative.
3. `docs/EXPLAIN_LIKE_IM_5.md`: the whole system as a story (a post room sorting letters), one page, zero jargon.
4. `docs/GLOSSARY.md`: every technical term used anywhere in the repo docs, UI or stage cards; one plain sentence
   and one example from this project each. Grep the docs and `stages.py` to make sure none is missing.
5. `docs/INTERVIEW_GUIDE.md`:
   - 30-second and 2-minute pitch; "why I built this for Tech Mahindra" using only the public sources in PLAN §2
     (open each link; quote only what it says; drop links that fail; never claim knowledge of internal systems).
   - Each component: what, how, why this way, file to open, the one-minute answer (expand EXPLAINABILITY.md).
   - Concepts from first principles with worked examples by hand: TF-IDF on 3 tiny messages, dot product and softmax
     with 3 classes, cross-entropy, summing probabilities per team, precision/recall and the threshold choice,
     calibration, embedding average, PSI on 3 bins, KS on 5+5 numbers, Luhn on one card number, transaction and
     unique constraint, REST status codes, Big-O of the main steps.
   - Results and how to read them; LR versus NN as measured, with the honest explanation; Hinglish and typo
     failures; error analysis from Q2.
   - "What reviewers found and what I fixed" from `AUDIT_LOG.md`, and failed experiments from `EXPERIMENTS.md`.
   - Honest limitations (short English texts, rubric labels, label noise, one test set reused by the gate, review
     selection bias, free hosting, SQLite, no authentication) and what production would need.
   - At least 60 questions with model answers: this project, ML basics, statistics and linear algebra, DSA/OOP/DBMS
     tied to files here, SQL to write by hand, REST and Git, deployment, responsible AI and privacy, scaling
     ("10,000 tickets a minute"), "what would you change", and a truthful answer to "was this built with AI tools?"
     (yes: planned and built with AI coding agents under the candidate's direction; the candidate's claim is
     understanding, verifying and being able to modify it; never claim sole authorship).
   - JD line → evidence table; demo script with timings and the fallback (PLAN §11, with real numbers).
   - Company sheet and 5 questions to ask the interviewer.
   - 5 hands-on exercises the candidate does alone (add a `[PAN]` redaction with a test; move one intent to another
     team and re-evaluate; change `tau_team` and read the coverage table; add a fifth drift indicator; add a SQL
     query for reviews per reviewer), each with the expected result so they can check themselves.
   - 5-day study plan, 2 hours a day, ending with a timed mock demo.
6. `docs/INTERVIEW_GUIDE.html`: the same content, one self-contained file (inline CSS, no external assets, print
   stylesheet with page breaks per section). Convert with the `markdown` package via a small script in `scripts/`.
7. Check `docs/DEPLOY.md` reads clearly for a first-time user; fix wording only. Done when: a link check and a "number without a source" grep both come back clean; `make test` still passes.
